# Runbook staging Hi-Ve · Phase 08.1A

Gunakan runbook ini setelah Ops mengotorisasi target. Topologi awal terdiri dari satu VM aplikasi 2 vCPU/4 GiB dan satu VM PostgreSQL 18 native 2–4 vCPU/8 GiB dengan SSD 60–100 GiB. Reservasi Compose API adalah batas maksimum 2 CPU dan 1536 MiB. Ukur kapasitas dengan profil pilot sebelum menaikkan batas. Data staging menggunakan fixture sintetis dan PostgreSQL tetap menyimpan state otoritatif.

## Artefak dan konfigurasi

1. Pilih commit yang lulus CI. Ambil artefak `hive-api-oci-<SHA>` atau bangun dengan `bash backend/scripts/build-staging-image.sh /absolute/output-dir <SHA>` melalui Buildx yang mendukung OCI exporter. Cocokkan label revision dan `release.json` dengan commit, platform, digest manifest dan metadata provenance BuildKit. Simpan digest image yang disetujui di catatan rilis. Jika Ops menyimpan image di registry, pastikan digest distribusi sesuai artefak yang ditinjau dan rekam digest registry yang akan dipakai. Attestation BuildKit menyediakan metadata build. Trust atas distribusi bergantung pada akses GitHub/registry dan verifikasi metadata rilis.
2. Simpan file environment dari [contoh](../deploy/staging/backend.env.example) di luar checkout dengan mode 0600. Gunakan nilai literal karena Compose memakai `env_file.format: raw`. Encode password DSN sebagai komponen URL. Mount CA PostgreSQL publik read-only pada `/run/hive/pg-ca.pem` dan pastikan UID 65532 dapat membacanya. Batasi akses ke Docker socket dan inspeksi container karena environment tersedia bagi operator Docker. Pisahkan OAuth client, SMTP, HMAC, pairing key dan pepper staging dari lingkungan lain. Key VAPID yang opsional mengikuti kanal secret yang sama.
3. Atur `HIVE_API_IMAGE` ke referensi `registry/repository@sha256:<64 hex>`, `HIVE_STAGING_ENV_FILE` ke file di atas, dan `HIVE_STAGING_PG_CA_FILE` ke path CA. Validasi referensi digest dan manifest Compose secara lokal. Pada target gunakan `docker compose -f backend/deploy/staging/compose.yaml config --quiet` agar hasil render env tidak muncul di log. [Compose env file](https://docs.docker.com/reference/compose-file/services/#env_file)

## PostgreSQL native dan migrasi

1. Gunakan private DNS dengan hostname yang ada di SAN sertifikat server. Pada firewall VM dan jaringan privat, izinkan TCP 5432 hanya dari IP VM aplikasi, jalur migrator admin dan sumber backup yang disetujui. Siapkan [postgresql.conf](../deploy/staging/postgres/postgresql.conf.example) dan [pg_hba.conf](../deploy/staging/postgres/pg_hba.conf.example). Ganti alamat contoh, batasi izin private key server, dan uji dari sumber yang diizinkan serta dari luar allowlist. Uji DSN dengan hostname benar, hostname salah, CA salah dan koneksi plaintext.
2. Untuk cluster staging baru, terapkan [bootstrap.sql](../deploy/staging/postgres/bootstrap.sql) sebagai admin PostgreSQL agar kepemilikan database berada pada `hive_migrator`. Atur kredensial tiap login melalui kanal Ops. Runtime memakai `hive_app`, migrator memakai `hive_migrator`, dan backup fisik memakai `hive_backup` dari jalur yang dibatasi. Pisahkan kredensial baca arsip/restore. Batasi port, role dan penggunaan credential file pada host yang bersangkutan.
3. Catat versi awal, base backup dan WAL yang dapat dipulihkan. Pastikan jalur shutdown serta rollback siap. Hentikan instance lama sebelum mengaktifkan lifecycle agar finalizer PIN yang mendahului 055 tidak memproses authorization epoch baru. Drain API dan hentikan checkout staging dalam jendela migrasi.
4. Gunakan satu eksekusi Tern v2.4.3 dari commit yang sama, role pemilik schema, `sslmode=verify-full`, CA privat, dan timeout. Isi `PGPASSFILE` mode 0600 melalui kanal Ops. Gunakan DSN **tanpa password** dan jalankan dari `backend/`.

   ```sh
   tern status --config migrations/tern.conf --migrations migrations --conn-string "$HIVE_MIGRATOR_DSN"
   tern migrate --config migrations/tern.conf --migrations migrations --conn-string "$HIVE_MIGRATOR_DSN"
   psql -X -v ON_ERROR_STOP=1 "$HIVE_MIGRATOR_DSN" -f deploy/staging/postgres/runtime-grants.sql
   ```

   Catat hasil `SELECT version FROM public.hive_schema_version`, constraint dan privilege channel. Uji nama host/CA salah dan koneksi role aplikasi. Pairing approved yang dibuat sebelum 055 memerlukan approval baru. Writer lama yang dapat memakai kolom lama melalui trigger 055 belum memenuhi syarat rollback aplikasi.
5. Jalankan `docker compose -f backend/deploy/staging/compose.yaml up -d --wait` setelah semua gate DB lulus pada jendela target yang disetujui. Probe lokal `GET /livez` memberi 204 selama listener hidup. `GET /readyz` memberi 204 hanya bila versi schema tepat sama dengan versi startup dan memenuhi minimum 055, lalu memberi 503 saat DB tidak tersedia, schema berubah atau drain dimulai. Tunnel pada VM aplikasi hanya meneruskan `/api/v1/`. Saat SIGTERM, runtime menutup admission, request HTTP diberi waktu selesai, socket menerima 1001 jika handshake masih berjalan, lalu klien menggunakan polling dan reconnect dengan cursor sebelumnya. Compose memberi grace period 25 detik. Uji kegagalan probe, restart, socket dan replay pada target.
6. Pantau HTTP request count, aggregate request duration, kesalahan 5xx, pool usage/wait, cleanup dan kegagalan Push dari log runtime. Default pool staging 12, dapat disesuaikan 2–32 sesuai budget DB. Timeout koneksi 4 detik, statement 12 detik, lock 3 detik. Ukur p95, DB lock wait, backlog worker, WAL dan disk secara terpisah pada target. Batasi akses dan retensi log. Access log ingress harus meredaksi query callback OAuth serta header/cookie yang berisi kredensial.

## Cloudflare, OIDC dan SMTP

- Landing memakai proyek Pages staging untuk `apps/landing/dist`. App dan Superadmin memakai Workers Static Assets. Build App dengan `HIVE_APP_API_ORIGIN` dan Superadmin dengan `HIVE_SUPERADMIN_API_ORIGIN` yang sama-sama menunjuk hostname HTTPS API staging. Gunakan hasil build yang sesuai SHA. Periksa static assets, service-worker update, CSP dan fallback 404. Untuk Pages, pilih metode build/upload sesuai proyek yang disetujui. [Template Landing](../../apps/landing/wrangler.staging.example.toml) · [Template App](../../apps/hi-ve-app/wrangler.staging.example.toml) · [Template Superadmin](../../apps/superadmin/wrangler.staging.example.toml) · [Cloudflare Pages](https://developers.cloudflare.com/pages/functions/wrangler-configuration/) · [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/binding/)
- Simpan konfigurasi [Tunnel](../deploy/staging/cloudflared.example.yml) dan credential file di luar checkout. Validasi ingress dengan `cloudflared tunnel --config <config> ingress validate`. Pastikan rule ingress memetakan hostname API dan `/api/v1/` ke loopback, memiliki catch-all 404, serta memblokir akses publik ke health endpoints. Verifikasi akses langsung ke port aplikasi dari luar VM gagal, WSS upgrade/reconnect bekerja, dan cache edge tidak menyimpan respons API. [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/configuration-file/)
- Tempatkan App, Superadmin dan API pada site HTTPS yang sama dengan origin berbeda. Registrasikan callback Google `https://<api>/api/v1/oidc/google/callback` untuk OAuth client staging. Uji Superadmin, Owner claim, login dan logout. Periksa cookie `__Host-`, Secure, HttpOnly, SameSite dan Path. Uji preflight yang sah serta penolakan origin asing, state salah/replay dan akses lintas sesi. Uji undangan email dari sender/domain staging melalui SMTP TLS langsung dengan verifikasi nama host.
- Pairing/PIN masih menggunakan peer koneksi. Di balik connector lokal, tes beberapa perangkat dari jaringan berbeda dan ukur pengaruh satu kuota peer bersama. Backend hanya boleh menerima header identitas peer setelah kontrak trusted ingress diverifikasi dan diuji. Periksa bahwa perubahan header forwarding pada request uji tidak menambah kuota.

## Rollback dan disaster recovery

- Saat migrasi gagal, tahan rilis, cek versi commit terakhir, perbaiki langkah yang gagal dan ulangi Tern melalui jalur migrator. Saat image gagal setelah migrasi, pertahankan schema dan gunakan hanya image ber-digest yang telah lulus gate staging 055, termasuk Pairing/PIN dan lifecycle. Jika tidak ada digest yang memenuhi gate itu, tahan trafik dan lakukan roll-forward. Binary yang tidak memeriksa epoch 055 tidak boleh dipakai.
- Untuk backup target, tetapkan jadwal base backup terenkripsi dengan `pg_basebackup -X stream --manifest-checksums=SHA256` melalui role backup/TLS. Jalankan `pg_verifybackup` dan simpan backup manifest. Ganti placeholder `archive_command` di contoh dengan integrasi penyimpanan off-VM yang disetujui. Handler harus idempotent, mendeteksi checksum berbeda untuk nama segmen yang sama dan mengembalikan sukses hanya setelah penulisan durable. Pantau `pg_stat_archiver`, ruang `pg_wal`, segmen terakhir, kesegaran base backup dan alarm. Uji akses kunci restore secara terpisah. RPO/RTO dan retensi menunggu keputusan Product Owner/Ops.
- Rehearsal target memakai VM/data directory PostgreSQL 18 terisolasi. Verifikasi base backup dan rangkaian WAL. Atur `restore_command` dengan hak baca arsip, `recovery_target_time` dalam UTC atau `recovery_target_name`, `recovery_target_action='pause'` dan `recovery.signal`. Validasi titik replay dan koneksi isolated, lalu cocokkan versi schema, count transaksi, ledger stok, histori audit dan kesehatan API pada clone. Catat RPO sebagai selisih state yang dapat dipulihkan dari waktu insiden simulasi. Catat RTO sampai smoke API berhasil. Promosi dan pemindahan trafik memerlukan keputusan terpisah agar dua writer tidak aktif pada timeline berbeda. [PostgreSQL 18 PITR](https://www.postgresql.org/docs/18/continuous-archiving.html)
